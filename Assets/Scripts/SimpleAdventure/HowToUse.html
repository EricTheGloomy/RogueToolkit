Unity Adventure Kit

Choose-your-own-adventure pages and one-off random events, in one system. A random event is just a page you arrived at by dice roll instead of by choice — same asset type, one thing to learn. Requirements and consequences are authored in the Inspector with dropdowns, so there's no code per event.

The files

Nine files sounds like a lot. Each is small and does exactly one thing, which beats three files of three hundred lines. The first four are what you author with; the next three run it.

  • Requirement.cs

    One condition. "Needs 10 gold", "must have the key", "must not have met the hermit".

  • Effect.cs

    One consequence. "Gain 10 gold", "lose 5 hp", "remember this happened".

  • Choice.cs

    One option. Edited inline inside its event — no asset per choice.

  • AdventureEvent.cs

    One page: text plus options. Also exactly what a random event is.

  • AdventureState.cs

    What the player has: flags, numbers, events already seen. Plus save data.

  • AdventureRunner.cs

    Runs it: current page, which options are valid, picking one.

  • AdventureBook.cs

    The asset your game points at. Knows every event, so it can load saves.

  • EventPool.cs

    A bag of random events, with weights and conditions.

  • AdventureExample.cs

    Zero-setup demo. Press Play, read the Console. Delete once it clicks.

Setup, about one minute

The demo builds its own adventure in code, so you can watch the system work before authoring a single asset. That's on purpose — see it move first, then learn the Inspector.

  1. Copy the nine .cs files into your project and let Unity compile.

  2. Add the Adventure Example component to an empty GameObject. Leave both slots empty. Press Play.

    You'll get a toll bridge with three options — one priced, one free, one greyed out with its reason — and the result of picking.

  3. Now author your own: right-click → Create → Adventure → Event. Make two or three. Fill in the body text, then add Choices — each one gets its own text, and a Goes To slot pointing at the next event.

    Leave Goes To empty for an option that ends the adventure.

  4. Create → Adventure → Book. Drag your first event into First Event, then right-click the Book asset and pick Collect Events.

    The Console tells you how many events it found. If that number is lower than you expect, some events aren't reachable through any choice.

  5. Drag the Book into the demo component's book slot and press Play again — it'll run your story instead of the built-in one.

The three memories

Everything the adventure remembers is one of these. Deliberately no more.

  • Flags

    On/off facts. Either the player has it or they don't.

    has_rusty_key
    spared_the_wolf
  • Stats

    Named numbers. Anything you never set is simply 0, so there's nothing to declare.

    gold = 40
    hp = 12
  • Seen

    Which events have already happened. This is what makes "only once" random events work.

    handled for you

All three live in AdventureState, which is a plain class — not a ScriptableObject. Same reason as ever: if you put progress on an asset, Unity writes it into the file while you playtest and every save slot shares it.

Pick a spelling for each key and stick to it. gold and Gold are two different numbers, and nothing will warn you.

Anatomy of a page

One event, three options, three different fates. This is the picture worth having in your head.

An event with an empty choices list is an ending — that's all "ending" means. So is an option whose Goes To is empty.

Events also have Effects On Arrival, which fire the moment the page appears, before the player picks anything. That's how a random event says "you stumble across 10 gold".

Recipe: the UI

The only part you have to write yourself, and it's short. The kit does the rules; this does the drawing.

AdventureUI.cs
public AdventureBook book;
public Text titleLabel;
public Text bodyLabel;
public Button[] optionButtons;   // four is usually plenty

private AdventureRunner runner;

void Start()
{
    runner = book.StartNewAdventure();
    Redraw();
}

void Redraw()
{
    if (runner.IsFinished())
    {
        gameObject.SetActive(false); // story over, close the window
        return;
    }

    AdventureEvent page = runner.GetCurrentEvent();

    titleLabel.text = page.GetTitle();
    bodyLabel.text  = page.bodyText;

    List<Choice> options = runner.GetVisibleChoices();

    for (int i = 0; i < optionButtons.Length; i++)
    {
        // Hide any spare buttons.
        if (i >= options.Count)
        {
            optionButtons[i].gameObject.SetActive(false);
            continue;
        }

        Choice option = options[i];
        bool allowed = option.IsAvailable(runner.state);

        optionButtons[i].gameObject.SetActive(true);

        // A locked option is shown but not clickable.
        optionButtons[i].interactable = allowed;

        string label = option.text;

        if (allowed)
        {
            string cost = option.DescribeCost();
            if (cost != "") label += "  (" + cost + ")";
        }
        else
        {
            label += "  - " + option.DescribeRequirements();
        }

        optionButtons[i].GetComponentInChildren<Text>().text = label;

        // Careful: clear old listeners or they stack up every Redraw.
        Choice captured = option;
        optionButtons[i].onClick.RemoveAllListeners();
        optionButtons[i].onClick.AddListener(() => OnOptionClicked(captured));
    }
}

void OnOptionClicked(Choice option)
{
    runner.Choose(option);
    Redraw();
}

The one real trap in there is the last bit: RemoveAllListeners() before AddListener. Skip it and every redraw adds another handler, so by page five one click fires five times.

Recipe: random events

Same events, same runner. The pool just decides which page you land on.

Create Adventure → Event Pool, then add entries. Each entry gets a weight (3 is three times as likely as 1), optional requirements, and an only once tick for one-off story beats hidden among the repeatable filler.

Firing one after a battle
public EventPool wildernessEvents;

public void OnBattleWon()
{
    // 30% chance of something happening at all.
    if (UnityEngine.Random.value > 0.3f) return;

    AdventureEvent evt = wildernessEvents.Draw(runner.state);

    // Always check for null. It is completely normal - it just means
    // nothing in the pool is eligible right now, usually because the
    // one-off events are all used up.
    if (evt == null) return;

    runner.Go(evt);
    adventureWindow.SetActive(true);
    Redraw();
}

A random event with no choices is a pure notification — "you find 10 gold" as an Effect On Arrival and nothing to pick. Give it a single "Continue" option with an empty Goes To if you want the player to have to acknowledge it.

Your own Player class

The kit owns its own numbers. Here's the two-line way to live with that.

You do not need an adapter or an interface. If your game already tracks gold and hp, copy them in before showing the event and read them back after:

Wherever you open the event window
// Before
runner.state.SetStat("gold", player.gold);
runner.state.SetStat("hp",   player.hp);

// ...player reads the page and picks an option...

// After
player.gold = runner.state.GetStat("gold");
player.hp   = runner.state.GetStat("hp");

Flags are usually best left living in AdventureState permanently — they're story memory, not player stats, and your game rarely needs them elsewhere.

The escape hatch

For the handful of things flags and numbers can't express.

Put anything you like in a choice's Custom Tag, then read it straight after Choose:

In OnOptionClicked
runner.Choose(option);

switch (runner.lastCustomTag)
{
    case "SPAWN_BOSS":    spawner.SpawnBoss();       break;
    case "PLAY_CUTSCENE": cutscene.Play();           break;
    case "OPEN_SHOP":     shopWindow.SetActive(true); break;
}

Redraw();

Resist the urge to route everything through here. A tag is invisible to the Inspector's dropdowns and can't be reasoned about — if something is really "spend 10 gold", make it an Effect so it shows up in DescribeCost() on the button.

Saving

runner.Save() gives you a plain object built for JsonUtility.

PlayerPrefs, fine for prototyping
void SaveGame()
{
    AdventureSave data = runner.Save();
    PlayerPrefs.SetString("adventure", JsonUtility.ToJson(data));
    PlayerPrefs.Save();
}

void LoadGame()
{
    string json = PlayerPrefs.GetString("adventure", "");
    if (json == "") { runner = book.StartNewAdventure(); return; }

    AdventureSave data = JsonUtility.FromJson<AdventureSave>(json);
    runner = book.Resume(data);

    Redraw();
}

Events carry a permanent hidden ID, same as the node graph kit, so renaming and moving your event assets is safe — the save stores the ID, not the name.

Two details you'd have had to discover the hard way, both handled: the stats dictionary is stored as two parallel lists, because JsonUtility flatly refuses to serialise a Dictionary; and Resume uses ResumeAt rather than Go, so a page's arrival effects aren't handed out again every time the player reloads.

Three gotchas

The first one is a design mistake; the other two are Unity being Unity.

Always leave one option with no requirements

If every option on a page is locked, the player is stuck staring at greyed-out buttons with no way out and no way back. Every page needs at least one unconditional escape — even if it's just "turn back". The demo script logs a warning when it hits this, so you'll catch it while testing.

Ctrl+D copies an event's hidden ID

Duplicating an event asset copies its ID too, so two events look identical to your save file. Collect Events on your Book detects this and names both assets; the fix is right-click the copy → Assign New Id. So after a round of duplicating, re-run Collect Events and check the Console.

Pool-only events need adding to the Book by hand

Collect Events walks your story from First Event through the choices — so it cannot see events that only exist inside an EventPool. Drag those into the Book's Also Include list or loading a save won't be able to find them. pool.GetAllEvents() hands you the list.

Outgrowing it

What this deliberately doesn't do, and when you'd notice.

Requirements with "or"
All requirements on a choice must be met — it's always AND. For "gold OR a favour owed", make two separate choices with the same text and destination. Slightly redundant, far easier to read in the Inspector than a condition tree.
Non-integer numbers, and clamping
Stats are whole numbers and can go negative. If hp shouldn't drop below zero, clamp it in your own code — the kit doesn't guess at your rules.
Randomness inside an outcome
A choice always does exactly what its effects say. "Pick the lock: 60% success" needs either two events and a coin flip in your own code, or a custom tag.
Writing prose in the Inspector
Fine for dozens of events, tiring for hundreds. At that scale writers usually want Ink or Yarn Spinner — real scripting languages for branching narrative, with proper text editors.
Sharing nodes with the graph kit
This is a separate system on purpose. The graph kit's connections carry no data, and here the choices are where all the data lives — that's exactly the split that made two kits the right answer instead of one.
