Unity Timeline Kit

Put things in order, press start, they fire one after another. The same list drives a real-time production queue or a turn-based card sequence — you choose per project by calling a different method. Cards, attacks, spawn waves, build orders, cutscenes.

The files

Six files. The first three are what you build with, the next two run it.

  • TimelineAction.cs

    One thing that can happen, and how long it takes. Inherit to add your own data.

  • Timeline.cs

    The ordered list. Add, remove, drag-reorder, capacity limits, timing maths.

  • TimelineSignal.cs

    "Something just happened." What the runner hands back to you.

  • TimelineRunner.cs

    Walks the playhead along and reports what it passed.

  • TimelineLibrary.cs

    The asset your game points at: the palette, the save lookup, optional presets.

  • TimelineExample.cs

    Zero-setup demo. Press Play, read the Console. Delete once it clicks.

Nothing to do with Unity's own Timeline package

Different thing entirely, and the names don't actually clash because Unity's live in the UnityEngine.Timeline namespace while these are global. But if you ever see an "ambiguous reference" error in a file that has using UnityEngine.Timeline;, that's the reason — drop that using, or write this kit's class as global::Timeline.

Setup, about one minute

The demo builds its actions in code, so you can watch it work before authoring anything.

  1. Copy the six .cs files into your project and let Unity compile.

  2. Add the Timeline Example component to an empty GameObject. Leave the slot empty. Press Play.

    You'll see the same five actions run twice — instantly turn-based, then over four real seconds.

  3. Now author your own: right-click → Create → Timeline → Action. Make a few, and set each one's Duration.

    Duration is seconds if you drive it in real time. If you're turn-based, leave everything at 1 and forget about it.

  4. Create → Timeline → Library. Drag every action into All Actions. If you want a fixed sequence rather than one the player builds, drag them into Preset Sequence too, in order.

    Then right-click the Library and pick Check For Problems.

  5. Drag the Library into the demo component's slot and press Play again — it'll run your preset instead of the built-in one.

Two ways to drive it

Same timeline, same actions, same signals. One method call is the whole difference.

  • Real time

    runner.Tick(Time.deltaTime)

    Called every frame from Update(). Durations mean seconds. Use it for production queues, attack windups, spawn waves, anything that plays out while the player watches.

  • Turn based

    runner.StepOne()

    Called when you want the next thing to happen. Durations stop mattering entirely. Use it for card games, puzzle games, or stepping through a scripted sequence on a keypress.

Both hand back the same list of signals. The runner never calls your methods and doesn't use C# events — you look through what it gives you, which makes the whole thing easy to follow and easy to test:

The entire integration
void Update()
{
    foreach (TimelineSignal signal in runner.Tick(Time.deltaTime))
    {
        if (signal.kind == TimelineSignal.Kind.ActionStarted)
        {
            DoTheThing(signal.action);   // <- your game happens here
        }
    }
}

Nine times out of ten ActionStarted is the only signal you care about. The other two are ActionFinished and TimelineFinished.

How the timing works

Nothing is stored. Start and end times are worked out by stacking the entries up, which is why editing the list can't corrupt the timing.

Because times are derived rather than stored, Move and RemoveAt automatically re-time everything after the change. There's no cached schedule to get out of sync — which is the usual way a hand-rolled sequencer starts producing mystery bugs.

A gap is a delayBefore on the following entry, not an entry of its own. Set it when you want breathing room in a scripted sequence; leave it at zero and things run back to back.

Recipe: production queue

Real time, with a progress bar. The classic strategy-game build queue.

BuildQueue.cs
public TimelineLibrary buildables;
public Image progressBar;
public Transform spawnPoint;

private Timeline queue;
private TimelineRunner runner = new TimelineRunner();

void Start()
{
    // Five things queued at once, no limit on total build time.
    queue = buildables.BuildEmpty(5, 0f);
}

// Wire this to your build buttons.
public void QueueUp(TimelineAction thing)
{
    if (!queue.Add(thing))
    {
        Debug.Log("Queue is full.");
        return;
    }

    // Start the queue if it was idle. Play() rewinds, so only do this when
    // nothing is running - otherwise you would restart the whole queue.
    if (!runner.IsPlaying()) runner.Play(queue);
}

void Update()
{
    foreach (TimelineSignal signal in runner.Tick(Time.deltaTime))
    {
        if (signal.kind == TimelineSignal.Kind.ActionFinished)
        {
            // A build FINISHES before the unit appears - that is the
            // difference between a queue and an attack sequence.
            BuildableAction built = (BuildableAction)signal.action;
            Instantiate(built.prefab, spawnPoint.position, Quaternion.identity);
        }
    }

    progressBar.fillAmount = runner.GetProgress();
}

Note this one reacts to ActionFinished, not ActionStarted — a tank appears when its build time is up, whereas a punch lands when it starts. Same kit, opposite signal.

Recipe: card sequence

Turn based. The player queues cards, then hits Resolve and watches them go off one at a time.

CardResolver.cs
public TimelineLibrary cards;

private Timeline played;
private TimelineRunner runner = new TimelineRunner();

void Start()
{
    // Three cards a turn, and durations are irrelevant because we step.
    played = cards.BuildEmpty(3, 0f);
}

public void PlayCard(TimelineAction card) { played.Add(card); }
public void TakeBack(int slot)            { played.RemoveAt(slot); }
public void Reorder(int from, int to)   { played.Move(from, to); }

// The "Resolve" button.
public void Resolve()
{
    runner.Play(played);
    StartCoroutine(ResolveOneAtATime());
}

// A coroutine gives each card a moment on screen. In a real game you would
// wait for an animation to finish rather than a fixed delay.
IEnumerator ResolveOneAtATime()
{
    while (runner.IsPlaying())
    {
        foreach (TimelineSignal signal in runner.StepOne())
        {
            if (signal.kind == TimelineSignal.Kind.ActionStarted)
            {
                CardAction card = (CardAction)signal.action;
                ApplyCard(card);
            }
        }

        yield return new WaitForSeconds(0.4f);
    }

    played.Clear();
    StartNextTurn();
}

Recipe: letting the player build it

The bit that makes it feel like a timeline rather than a script.

CanAdd is what you hang your UI off — it accounts for both limits at once, so a palette button can grey out before the player finds out the hard way:

Refreshing the palette
void RefreshPalette()
{
    for (int i = 0; i < paletteButtons.Length; i++)
    {
        TimelineAction action = library.allActions[i];

        paletteButtons[i].interactable = timeline.CanAdd(action);
    }

    // "3 / 5 slots"  or  "2.5s / 4.0s used"
    slotsLabel.text = timeline.Count + " / " + timeline.maxEntries;
    lengthLabel.text = timeline.GetTotalDuration().ToString("0.0") + "s";
}

For drag-to-reorder, Move(from, to) is all you need — and because start times are derived rather than stored, everything after the moved entry re-times itself with no bookkeeping on your side.

Set maxTotalDuration rather than maxEntries when you want the interesting decision to be "three quick jabs or one big swing", which is usually the better game.

Waiting for an animation

For when the real length isn't a number you know up front.

Tick Wait For Finish on an action and the timeline stops dead the moment it starts. Time genuinely doesn't move — Tick() does nothing however long you tick it — until your code says otherwise:

Releasing a parked action
// ...in your signal handler
if (signal.kind == TimelineSignal.Kind.ActionStarted)
{
    animator.Play("BigSwing");
    // The timeline is now parked. runner.IsWaiting() is true.
}

// Called from an Animation Event at the end of the clip.
public void OnSwingAnimationDone()
{
    foreach (TimelineSignal signal in runner.FinishCurrent())
    {
        Handle(signal);
    }
}

Use it for animations, player confirmations, and server replies. StepOne() treats a parked action as done, so a turn-based game needs no special case at all.

Saving

Only worth doing for a queue that should survive quitting — a battle timeline usually shouldn't.

PlayerPrefs, fine for prototyping
void SaveQueue()
{
    PlayerPrefs.SetString("buildQueue", JsonUtility.ToJson(queue.Save()));
    PlayerPrefs.Save();
}

void LoadQueue()
{
    string json = PlayerPrefs.GetString("buildQueue", "");
    if (json == "") return;

    queue.Load(JsonUtility.FromJson<TimelineSave>(json), buildables);
}

Actions carry a permanent hidden ID, same as the other two kits, so renaming and moving your action assets is safe. Anything the library no longer knows about is skipped rather than crashing, so deleting a buildable in an update won't break old saves.

The playhead position isn't saved — a loaded queue starts from the beginning. If you need mid-action resume, save runner.GetPosition() yourself alongside it.

Three gotchas

One is a design constraint, two are easy mistakes.

Only one action runs at a time

That's the point of "one after another", and it's deliberate — it's what keeps the whole thing comprehensible. If you need two things genuinely overlapping, use two runners with two timelines. Don't try to bend this one; overlapping sequencers are where simple timeline code turns into a monster.

Play rewinds — don't call it to resume

Play() always starts from the beginning. Adding to a queue that's already running and then calling Play() again restarts the lot. Check IsPlaying() first, as the production-queue recipe does. To un-pause, use Resume().

Ctrl+D copies an action's hidden ID

Duplicating an action asset copies its ID too, so two actions look identical to your save file. Right-click your Library → Check For Problems catches it, along with empty slots and preset actions missing from the palette. Run it after a round of duplicating.

Two things you don't have to worry about, because they're handled: a big deltaTime from a lag spike never skips an action — one Tick reports everything the playhead passed, in order. And ActionFinished always arrives before the next ActionStarted at a boundary, so you can always clean up one thing before the next begins.

Outgrowing it

What this deliberately doesn't do.

Parallel tracks
One action at a time, as above. Music, VFX and gameplay all firing at once on separate lanes is a real thing to want — that's when you graduate to Unity's own Timeline package, or run several of these side by side.
Scrubbing backwards
The playhead only goes forwards. Rewinding would mean every action knowing how to undo itself, which is a much bigger idea than this kit.
Conditions on entries
Every action on the list fires. For "only if the player still has mana", check it in your handler and ignore the signal — or borrow Requirement from the adventure kit, which was built for exactly that.
Actions that change the list mid-play
Editing a timeline while its runner is playing it will re-time things under the playhead and confuse the runner. Queue up changes and apply them between runs, or use a second timeline.
