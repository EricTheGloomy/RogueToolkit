Unity Polyomino Kit

Things on a grid that know where they are, what's next to them, and what's on their row and column — and interact accordingly. Backpack inventories, base building, tile puzzles, card boards. Pieces can be tetromino-shaped and rotatable, or plain 1×1 squares; placed by the player, or fixed in place by the game. You draw shapes as text, so there's no custom Inspector to write.

Why it's not as hard as it looks

It's three problems that don't touch each other. Tangled together they're horrible; separated, none of them is difficult.

  • Shape and rotation

    Pure maths on a set of squares. Knows nothing about Unity or your game, which is why it can be tested against shapes drawn on paper.

  • The board

    Does it fit? What's in this square? A 2D array of references and some bounds checks. Genuinely the easy bit.

  • The neighbour rules

    Pure data you author in the Inspector with dropdowns. No code per piece, and both "I gain" and "I give" directions work.

The files

Six files, one per idea.

  • PieceShape.cs

    Text → squares → rotations. Pure maths, no Unity involved.

  • AdjacencyRule.cs

    One "look around me" rule, plus the stat/amount pair.

  • GridPiece.cs

    One kind of piece: shape, tags, base stats, rules.

  • PieceGrid.cs

    The board, plus PlacedPiece — one copy sitting on it.

  • GridEvaluator.cs

    Works out what everything is worth, and explains why.

  • GridExample.cs

    Zero-setup demo. Press Play, read the Console. Delete once it clicks.

Setup, about one minute

  1. Copy the six .cs files into your project and let Unity compile.

  2. Add the Grid Example component to an empty GameObject and press Play.

    You'll get a 5×5 bag drawn in the Console, a sword's rotations, four pieces packed in, a refused move, and the full stat breakdown before and after.

  3. Now author your own: right-click → Create → Grid → Piece. Draw the shape in the Shape Mask box, add a tag or two, and give it some Base Stats.

    Right-click the asset and pick Print Shape And Rotations to check you drew what you meant.

  4. Add Rules to make pieces care about their neighbours. The recipe table below covers most of what you'll want.

Shapes as text

The trick that keeps this kit small. No custom editor, and you can read a shape at a glance in the Inspector.

Rotations that come out identical are dropped. A 2×2 square reports one rotation and a straight line reports two, so rotating in your UI never appears to do nothing. Rotation numbers also wrap in both directions, which means rotation++ and rotation-- are safe forever with no range checks.

The board

Boards are drawn as text too, with # for a square that can't be used.

An awkwardly-shaped rucksack
PieceGrid bag = PieceGrid.FromMask(
    "....#\n" +
    ".....\n" +
    ".....\n" +
    ".....\n" +
    "#....");

// Or just a plain rectangle:
PieceGrid chest = new PieceGrid(8, 4);

(0,0) is the top-left square, x goes right and y goes down. No mental flipping between the mask you drew and the coordinates you pass in.

Two methods do almost all the work. CanPlace tells you whether a piece fits — that's what colours your drag preview green or red — and Place puts it down, handing back a PlacedPiece or null:

Placing and moving
if (bag.CanPlace(sword, rotation, x, y)) { preview.color = Color.green; }

PlacedPiece placed = bag.Place(sword, rotation, x, y);   // null if it did not fit
PlacedPiece loot   = bag.PlaceAnywhere(potion);          // your "pick up" button

bag.Remove(placed);

// Moving hands back a NEW placed piece. If it does not fit you get null and
// nothing changes, so a failed drag cannot lose the player's item.
PlacedPiece moved = bag.TryMove(placed, newRotation, x, y);
if (moved != null) placed = moved;

When you're wondering why something won't go where you expect, print the board before reaching for the debugger:

The fastest debugging you will do all week
Debug.Log(bag.ToText() + "\n" + bag.ToLegend());

// ABBD#
// ABBDD
// AC..D
// .....
// #....
// A = Sword, B = Shield, C = Ruby Gem, D = Rations

1×1 pieces, and things the game places

Two variations that cover a whole other family of games: city grids, slot inventories, board layouts.

If everything is 1×1

Perfectly normal, and probably the commonest case. Just use "X" as the shape mask. Every piece then reports one rotation, so the whole rotation system quietly gets out of your way — PlaceAnywhere stops trying alternatives, rotating in your UI correctly does nothing, and you can pass 0 for rotation everywhere and forget it exists.

You keep the part that actually matters: pieces knowing their location, their neighbours, their row and column, and how they interact. Nothing else in the kit changes.

Things the game places

Terrain, obstacles, a pre-built town hall, a well in the middle of the map. They take part in every rule but the player must not be able to move or bulldoze them:

Laying out a level
// The game lays out the terrain first...
PlacedPiece well = map.PlaceLocked(wellPiece, 0, 2, 2);
PlacedPiece rock = map.PlaceLocked(rockPiece, 0, 0, 4);

// ...then the player builds on it.
PlacedPiece hut = map.Place(hutPiece, 0, 1, 1);

map.Remove(well);              // false - refused, it is the game's
map.TryMove(well, 0, 4, 4);    // null  - refused
map.Remove(hut);               // true  - the player's own, fine

map.ClearUnlocked();           // "reset my layout" - terrain survives
map.RemoveEvenIfLocked(well);  // your own code can still destroy it

Locked pieces are ordinary pieces as far as the rules engine is concerned — they give and receive bonuses exactly like anything else. So a well that buffs everything within two squares is one PlaceLocked call and one aura rule.

In ToText() they draw as a lowercase letter and the legend marks them (fixed), so one glance tells you what the player owns:

A city grid of 1×1 pieces
// .....
// .E...     a = Well (fixed), b = Rock (fixed)
// .CaDF     C = House, D = House, E = Park, F = Factory
// .....
// b....
//
// House at 1,2: happiness -1, population +7
//     +4 population base
//     +1 population from Well within 2
//     +2 population from 1 touching park
//     -1 happiness from 1 on the same row factory

That example is four rules and six Place calls — location, neighbours, row effects and an aura from a fixed feature, all from the same kit.

Writing rules

Read a rule left to right like a sentence. All of it is Inspector dropdowns — you write no code per piece.

"For each touching piece tagged weapon, give me +1 attack." Here's how the common effects come out:

Recipes
What you wantscopetagtargetcountingamount
+1 attack per touching weapon TouchingweaponMePerNeighbour1
+5 defence if next to any food TouchingfoodMeOnceIfAnyFound5
−2 if nothing is touching me Touching(empty)MeOnceIfNoneFound−2
Buff everything within 2 squares WithinDistance 2(empty)EachMatchingNeighbour—2
Curse my orthogonal neighbours Touching(empty)EachMatchingNeighbour—−2
+1 gold per gem on my row SameRowgemMePerNeighbour1

An empty tag means "any piece at all". Negative amounts are debuffs. counting is ignored when the target is EachMatchingNeighbour — each match gets the amount once.

Both directions work, and that matters. "I like being near weapons" is a rule on the sword; "I make my neighbours stronger" is a rule on the gem. Use whichever reads more naturally for the piece you're designing rather than contorting one into the other.

Touching means sharing an edge. TouchingOrDiagonal also counts corners. WithinDistance is an aura, counting a diagonal step as one.

Recipe: drag and drop

The four moments that matter. Everything else is your own UI.

BagUI.cs
private PieceGrid bag;
private PlacedPiece dragging;   // null when nothing is being dragged
private int dragRotation;

// 1. Picked up: take it off the board so it cannot block itself.
public void OnPickUp(PlacedPiece placed)
{
    dragging = placed;
    dragRotation = placed.rotation;
    bag.Remove(placed);
    Redraw();
}

// 2. R to rotate. No range check needed - rotation numbers wrap.
void Update()
{
    if (dragging != null && Input.GetKeyDown(KeyCode.R)) dragRotation++;
}

// 3. Hovering: colour the preview.
public void OnHover(int x, int y)
{
    if (dragging == null) return;

    bool fits = bag.CanPlace(dragging.piece, dragRotation, x, y);
    preview.color = fits ? Color.green : Color.red;
}

// 4. Dropped.
public void OnDrop(int x, int y)
{
    if (dragging == null) return;

    PlacedPiece placed = bag.Place(dragging.piece, dragRotation, x, y);

    if (placed == null)
    {
        // Would not fit. Put it back exactly where it came from - never
        // leave the player's item in limbo.
        bag.Place(dragging.piece, dragging.rotation, dragging.x, dragging.y);
    }

    dragging = null;
    Redraw();
}

void Redraw()
{
    // Recalculate from scratch. Do not try to keep totals updated as you go.
    GridReport report = GridEvaluator.Evaluate(bag);

    attackLabel.text = "Attack " + report.GetTotal("attack");
    defenceLabel.text = "Defence " + report.GetTotal("defence");

    // ...draw the squares from bag.GetAllPieces()
}

Taking the piece off the board on pick-up is the detail people miss. Leave it on and it blocks its own destination, so nudging something one square to the left mysteriously fails. (If you'd rather not remove it, TryMove handles the same problem for you by ignoring the piece being moved.)

Recipe: tooltips that explain themselves

The reason the evaluator returns explanations rather than just numbers.

Hovering a piece
public void ShowTooltip(PlacedPiece placed)
{
    GridReport report = GridEvaluator.Evaluate(bag);
    PieceReport mine = report.GetReportFor(placed);

    string text = placed.GetDisplayName() + "\n" + mine.DescribeStats();

    foreach (string line in mine.explanations)
    {
        text += "\n  " + line;
    }

    tooltipLabel.text = text;

    // Sword
    //   attack +6
    //     +3 attack base
    //     +1 attack from 1 touching armour
    //     +2 attack from Ruby Gem within 2
}

That breakdown is also how you debug a rule that isn't firing — you can see at a glance whether it matched nothing, or matched and gave the wrong amount.

Four gotchas

The first is the classic bug in systems like this. It has a test named after it.

Neighbours are distinct pieces, not shared edges

A 1×3 sword lying along a 2×2 shield touches it across two squares — but it's still one shield, and a "+1 per touching armour" rule gives +1, not +2. The kit counts distinct pieces. Worth knowing because if you ever write your own version of this, counting edges is the mistake you'll make.

TryMove hands back a new PlacedPiece

The old one is off the board and no longer valid. Always use the returned value. On failure it returns null and changes nothing, so a failed drag can't lose the player's item — but a stale reference will silently stop working.

Re-evaluate from scratch, always

Don't try to keep totals updated incrementally as pieces move. One piece moving can change three others' bonuses through an aura, and incremental updates are exactly where this kind of system rots. On a board a human can arrange, Evaluate costs nothing.

Ctrl+D copies a piece's hidden ID

Same as the other kits: duplicating a piece asset copies its ID, so two pieces look identical to a save file. Right-click the copy → Assign New Id. And Print Shape And Rotations on any piece is the quickest way to confirm you drew what you meant.

Outgrowing it

What this deliberately doesn't do.

Mirrored pieces
Only the four rotations, no flipping. An L and its mirror image J are two different pieces here — which is how Tetris treats them anyway. If you need flipping, add a mirrored mask as a second asset.
Rules that depend on other rules
Every rule reads the board, never another rule's result, so evaluation is one clean pass. "+1 attack for each neighbour that already has +2 attack" isn't expressible, and that's on purpose — those chains are where the numbers become impossible to reason about.
Hex or triangular grids
Squares only. Hexes need different neighbour maths throughout, though the shape-as-text and rules-as-data ideas would carry over.
Saving a packed board
Pieces carry the same hidden IDs as the other kits, so it's straightforward — save each placed piece's id, rotation, x, y and locked flag, and place them again on load. Ask and I'll add it.
Very large boards
Evaluation walks every piece against every rule. Fine for hundreds of pieces; if you're at thousands and evaluating every frame, cache the report and only recompute on change.
