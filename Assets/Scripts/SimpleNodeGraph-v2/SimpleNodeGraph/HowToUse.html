Unity Node Graph Kit

Four small scripts that turn a pile of assets into a connected graph — a skill tree, a world map, a dialogue tree. The whole idea: a node is an asset with a list of the nodes it connects to. That list is the graph. There is no clever graph class anywhere.

The files

Drop all four anywhere under Assets. No folder structure required, no namespaces to import.

  • GraphNode.cs

    One node. A title, a list of neighbours, a hidden ID. Inherit from it to add your own data.

  • GraphState.cs

    The player's progress: which nodes are unlocked. A plain List plus small helpers.

  • NodeGraph.cs

    One asset per tree. Holds every node, starts new games, finds routes.

  • GraphExample.cs

    A throwaway test script that prints to the Console. Delete it once things click.

Setup, about five minutes

Do this once with three throwaway nodes before you build anything real. Seeing the Console output is what makes the rest obvious.

  1. Put the four .cs files in your project and let Unity finish compiling.

  2. In the Project window: right-click → Create → Graph → Node. Make three, named Root, Strength, HeavyArmor.

  3. Select Root. In the Inspector, drag Strength into its Connected To list. Then select Strength and drag HeavyArmor into its list.

    Connections are one-way. Root → Strength does not mean Strength → Root.

  4. Right-click → Create → Graph → Node Graph. Drag Root into its Starting Nodes, then right-click the asset itself and pick Collect Nodes.

    The Console should say found 3 nodes. If it says 1, your connections aren't wired up. Re-run this whenever you add nodes — it also checks for the duplicate-ID problem below.

  5. Make an empty GameObject, add the Graph Example component, drag your Node Graph asset into its slot, and press Play.

    You'll see Root unlocked, Strength available, HeavyArmor not — then Strength gets unlocked and HeavyArmor becomes available.

How it thinks

Two objects, and keeping them apart is the entire design.

The graph is your assets. It never changes while the game runs — it's the map. The state is a list of unlocked nodes that lives in memory and goes into your save file — it's the progress.

Everything else follows from one question: is this node touching something I already own? That's CanUnlock, and it's literally a loop over your unlocked list asking each node "is this one in your connectedTo?"

Everything you can call

That's the complete surface. If something isn't here, it doesn't exist. There's also one right-click item on a node asset — Assign New Id — which you'll only need in the duplicate-asset case below.

Recipe: skill tree

Add your own node type, then gate unlocking on both the graph rule and your cost rule.

SkillNode.cs
using UnityEngine;

[CreateAssetMenu(menuName = "Graph/Skill Node")]
public class SkillNode : GraphNode
{
    public int cost = 1;
    public Sprite icon;
    public string description;
}

Now create Skill Node assets instead of plain Node assets. Everything in the kit still works, because a SkillNode is a GraphNode.

One rule if you ever add your own OnValidate to a subclass: write it as protected override void OnValidate() and start the body with base.OnValidate();. That's the method that hands out hidden IDs, so skipping it means your nodes never get one.

SkillTreeUI.cs
public NodeGraph tree;
public int pointsAvailable = 3;

private GraphState state;

void Start()
{
    state = tree.CreateNewState();
}

// Call this from your skill button's OnClick.
public void OnSkillClicked(GraphNode node)
{
    SkillNode skill = (SkillNode)node;

    if (!state.CanUnlock(node))
    {
        Debug.Log("You need the skill before it first.");
        return;
    }

    if (pointsAvailable < skill.cost)
    {
        Debug.Log("Not enough points.");
        return;
    }

    pointsAvailable -= skill.cost;
    state.Unlock(node);
    RefreshButtons();
}

void RefreshButtons()
{
    // Three visual states, straight from the two methods:
    foreach (GraphNode node in tree.allNodes)
    {
        bool owned     = state.IsUnlocked(node);
        bool available = state.CanUnlock(node);

        // owned     -> bright
        // available -> outlined and clickable
        // neither   -> greyed out
    }
}

Recipe: world map

Same kit, two differences: connections go on both nodes, and you use FindPath.

For a map, add each road to both locations' Connected To lists — Home lists Forest and Forest lists Home. Then "unlocked" means "discovered", and passing the state to FindPath gives you travel restricted to places the player knows.

TravelController.cs
public NodeGraph map;

private GraphState discovered;
private GraphNode playerLocation;

void Start()
{
    discovered = map.CreateNewState();
    playerLocation = map.startingNodes[0];
}

public void TravelTo(GraphNode destination)
{
    // Third argument = only walk through discovered places.
    List<GraphNode> route = map.FindPath(playerLocation, destination, discovered);

    if (route == null)
    {
        Debug.Log("You don't know a route there yet.");
        return;
    }

    Debug.Log("Travelling " + (route.Count - 1) + " steps.");

    foreach (GraphNode stop in route)
    {
        Debug.Log("  ...through " + stop.GetTitle());
    }

    playerLocation = destination;
    Arrive(destination);
}

void Arrive(GraphNode location)
{
    // Arriving reveals the neighbours, which is your fog of war.
    foreach (GraphNode neighbour in location.connectedTo)
    {
        discovered.Unlock(neighbour);
    }
}

route.Count - 1 is the number of steps — the list includes where you started, so a three-item route is two moves.

Recipe: dialogue

The odd one out: dialogue needs no GraphState at all. You just walk the list.

A dialogue node's connectedTo list is its player choices, in order. There's no unlocking involved — you only ever track which line you're on.

DialogueRunner.cs
// Your node type:
//   public class DialogueNode : GraphNode
//   { public string speaker; public string line; }

public NodeGraph conversation;

private GraphNode currentLine;

void Start()
{
    currentLine = conversation.startingNodes[0];
    Show();
}

void Show()
{
    DialogueNode line = (DialogueNode)currentLine;
    Debug.Log(line.speaker + ": " + line.line);

    if (currentLine.connectedTo.Count == 0)
    {
        Debug.Log("[end of conversation]");
        return;
    }

    // One button per choice.
    for (int i = 0; i < currentLine.connectedTo.Count; i++)
    {
        GraphNode choice = currentLine.connectedTo[i];
        Debug.Log("  [" + i + "] " + choice.GetTitle());
    }
}

public void Choose(int index)
{
    currentLine = currentLine.connectedTo[index];
    Show();
}

The catch: this puts the choice text on the destination node rather than on the connection. Usually fine. If you need a choice that reads differently from the line it leads to, make the choice its own little node in between.

Saving

Save() hands you a list of strings. Where it goes is up to you.

You can't put a ScriptableObject reference in a save file, so each node quietly carries a permanent random ID — a 32-character string like 9f2c4a17e8b34d0e91c3… — created once when you make the asset and never changed again. It's hidden in the Inspector because there's no reason to touch it.

The upshot: renaming and moving your node assets is completely safe. Call a skill Strength today and Brawn next month; existing saves keep working, because the name was never what got written down.

PlayerPrefs, fine for prototyping
void SaveGame()
{
    // A list of node IDs, one per unlocked node.
    List<string> ids = state.Save();

    PlayerPrefs.SetString("unlockedSkills", string.Join(",", ids.ToArray()));
    PlayerPrefs.Save();
}

void LoadGame()
{
    string stored = PlayerPrefs.GetString("unlockedSkills", "");
    List<string> ids = new List<string>(stored.Split(','));

    state.Load(ids, tree);
}

For a real save system, put that List<string> in whatever class you serialise to JSON. Load quietly skips any ID it can't find, so if you delete a skill in an update, old saves load fine and just lose that one unlock rather than crashing.

Two gotchas

Both cost people an afternoon. Neither is obvious from the code.

Never put progress on a node

Adding public bool unlocked to GraphNode is the obvious move and it breaks two ways. Unity writes the value into the asset file while you playtest, so your tree stays half-unlocked next time you hit Play; and every save slot shares one value. That's the whole reason GraphState is a separate object.

Duplicating a node with Ctrl+D copies its ID

Ctrl+D is the fast way to make a similar node, and it copies the hidden ID along with everything else — so two different skills look like the same skill to your save file. Collect Nodes checks for this and logs an error naming both assets and the fix: right-click the copy and choose Assign New Id. So after a round of duplicating, re-run Collect Nodes and glance at the Console.

Outgrowing it

Things this deliberately doesn't do, and when you'd care.

Travel costs
FindPath counts steps, not distance or fuel. If crossing a mountain should cost more than crossing a field, you need a weighted search instead.
Data on the connection
Connections carry nothing but "these two are linked". Conditions like "only if the player has the key" have to live on a node, not on the link between two.
A visual editor
Dragging assets into lists gets tedious past roughly fifty nodes. Rather than writing your own canvas — genuinely a thousand-plus lines — install xNode, which is free and does exactly this.
Speed
These are List lookups, which get slower as the graph grows. Irrelevant for hundreds of nodes and a menu that refreshes on click; worth revisiting if you're pathfinding across thousands every frame.
